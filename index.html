The green screen that was lying.

A page told managers everything was fine while showing them only a slice of the data. I found why, fixed it, and proved the fix against the live system.

One day the goals page showed a calm green message: nothing needs action this month. It was wrong. A large share of that month's goals had not even been started.

Nothing had crashed. The database layer returns at most 1,000 rows per request and reports the real total only in a response header that my code never read. Once the table grew past 1,000 rows, every screen kept working and quietly showed a slice of the data, all of it from a single month. Eight other screens were reading the same slice.

The fix was to fetch page after page until the count matched the total, with a stable sort so no row is skipped or repeated between pages. Then I checked it against the live system: every row present, zero duplicates, all twelve months.

Try it: open the goals page

Each bar is one month of goals. Illustrative numbers.

A confident all-clear is worse than an error. Nobody investigates a green screen.

A login inside a link.

A PDF link carried the user's whole login. I replaced it with a two-minute, single-file token and made every login revocable.

To open a PDF cover sheet in a new tab, the link carried the user's login token in its address. It worked. It also meant the link was the login: addresses end up in browser history and forwarded messages, and that token was good for the whole account.

I replaced it with a token that does one thing: open that one file, for two minutes. A few days earlier I had made logins revocable. Each account carries a version number and every token is stamped with it. Changing a password or a role, or deactivating an account, raises the number, so every older token stops working at once.

Try it: sign out everywhere

One account, signed in on two devices. A simplified model of the real check.

A token should do the least it needs to, for the shortest time.

Stop translating chai to tea.

A translation that looked harmless was putting the wrong product in the cart. I caught it by testing what the user would actually receive.

Early on I translated Hindi words to English before searching: jeera to cumin, haldi to turmeric, chai to tea. I tested "chai" against "tea" on one app, got the same five products back, and decided the translation was harmless.

It wasn't. The ranker scores how many words of the search appear in a product's name, then lets price break ties. "Masala tea" matched a ₹99 box of instant premix as well as it matched loose masala chai at ₹170, so the cheaper one won. Someone who wrote "masala chai" would have got sachets.

I stopped translating chai, then tested every other translation the same way. Most made no difference. One was essential: searching "pyaz" returned baby potatoes, while "onion" returned onions.

Try it: the list says "masala chai"

The same search results are not the same decision. Test what the user actually gets.

Three long labels took down a whole day.

Three slightly-too-long labels cancelled a whole day's digest. I changed the pipeline so one bad part costs only that part.

On 1 August it published nothing. The cause was three image labels that were slightly over a length limit. One check treated that as fatal and threw away the article's image plan, and a later step refused to publish any digest with a missing plan. The renderer already trimmed long labels, so the check was guarding against a problem that did not exist.

The code had merged two questions: is this one image usable, and should we publish at all? I separated them. An article with a bad image plan now goes out without an image, never with a fake one, and everything else publishes as normal.
